# P1 双纹理位移 vs 0.86 scissor：真机 A/B 性能报告

日期：2026-10-31
结论：**P1 相对原方案没有可测的性能提升，也没有回退**——帧率、帧间隔、CPU、内存、启动
全部落在同一噪声区间内。P1 的收益是**视觉**（旧页整体位移 vs 旧页静止），不是性能。

## 1. 测试条件

| 项 | 值 |
|---|---|
| 设备 | vivo V2463A（PD2463），USB adb |
| 系统 | Android 17（SDK 37） |
| 屏幕 | 1440×3168，density 600（DPR 3.75），peak refresh 144Hz |
| 应用 | `org.jmcomic.jmcomic` 0.87（versionCode 103487，minSdk 34，arm64-v8a debug） |
| 对比组 | A = P1 位移（`ScissorBaseline=False`）；B = 0.86 的 scissor 揭示（`True`） |
| 测试页面 | 首页 ↔ 设置（同一对页面，内容已加载） |
| 操作方式 | adb `input tap`：菜单 → 设置 → 面包屑返回，每步间隔 1.0s |
| 样本 | 预热 2 轮后采集；A1 20 次转场、A2 22 次、B 18 次（稳态）；另有 A 44 次 / B 25 次批量样本 |
| 控制 | 同一台设备、同一份数据、`install -r` 保留数据；屏幕常亮；温度未主动控制（A-B-A 交叉抵消漂移） |
| 采集 | 应用内探针：`FrameTick` 时间戳、`/proc/self/stat` 的 utime+stime、覆盖层 `PaintMs/PaintCount`；每次转场输出一行 `[P1PERF]`，探针在测试后已回滚，发布 APK 不含 |

**覆盖范围说明**：本次采集到的 84+ 次转场全部是 `type=1`（前进方向的合成路径）。
原因是既有逻辑 bug（见 §4.1）：返回键走 `SwitchWidgetLast()` 时先把 `subStackList` 裁到目标页，
再调 `SwitchWidgetByIndex()`，导致方向恒为 `LeftToRight`。因此 P1 的**后退分支**
（`nextX = off-W`）只有单元测试覆盖，未做设备级帧率测量；该分支与前进分支的绘制量、
调用次数完全对称（同样 2 次 draw，仅偏移取反），性能预期一致，但**修掉方向 bug 后应补测一次**。

指标定义：

* **fps** = (帧数−1)/首末帧间隔；是"应用侧产出帧"，Qt 不锁 vsync，可能略高于刷新率。
* **p50/p95/max**：相邻 `FrameTick` 间隔（ms）。
* **CPU/次**：转场 250ms 窗口内**整进程**（所有线程）CPU 时间增量，含并发的封面加载等后台工作。
* **paint/帧**：GPU 覆盖层每帧 CPU 侧提交耗时（`PaintMs` 增量 / `PaintCount` 增量）。
* **启动**：`am start -W` 的 TotalTime（activity 首帧，3 次冷启）。
* **内存**：`dumpsys meminfo` 的 TOTAL PSS。

**判读**：A1 与 A2 是同一版本、同一脚本、间隔 15 分钟的两次测量，fps 相差 6.6%——

p50 的 B 侧均值被一次 14.6ms 离群拉高，按中位数（6.4 vs 6.5）几乎没有差别。

## 3. 为什么预期就是"没有提升"

两条路径的每帧工作量本来就相同：

* 都是 **2 次 draw call、零 uniform/顶点上传**；
* 可见填充面积都是一屏：scissor = 旧页全屏 + 新页窄带；位移 = 旧页可见部分 + 新页可见部分，
  屏幕外部分被光栅化裁掉；
* 差异只是一个**视口变换**（`setViewport` 的 x 偏移）对一个 `setScissor`，GPU 侧成本同量级；
* CPU 侧 `paint/帧` 实测都是 0.10ms。

P1 的目标是"旧页也动"的观感，不是缩短帧时间。真正影响帧率的是快照 `render()`、封面解码、
列表构建等（本次 CPU 204ms/250ms 窗口，主要来自这些后台工作）。

## 4. 异常与回退情况

1. **后退方向被标成前进（既有问题，非 P1）**：全部 84+ 次转场的 `dir` 都是 `fwd`。
   `MainView.SwitchWidgetLast()` 先把 `subStackList` 裁到目标页，再调 `SwitchWidgetByIndex()`，
   导致 `oldIndex/newIndex` 都算成 0 → 方向恒为 `LeftToRight`。
   后果：**返回时两页也按"前进"方向滑**。scissor 时代同样存在，但位移把整页运动放大后更显眼。
   建议单独修：先取方向、再裁栈（或把方向作为参数传入）。
2. **偶发长帧**：A 批量 44 次里 1 次、B 25 次里 1 次出现 n=14~18、fps 54~71、max 101ms，
   同期有封面解码/网络回调；两组都会出现，判断为后台工作尖峰，不是 P1 回退。
3. **p95 约 20–22ms**：每组每次转场约 2–3 帧 >16.7ms，两组一致。注意 0.86 文档里的
   p95=16.3ms 是 Android 14 上测的，本机已升到 Android 17，绝对值不可直接跨版本比较。
4. **无 GPU 降级**：两个变体的 logcat 均无 `GpuAnimCover` / `watchdog` / `fallback` /
   `Invalid texture upload`；`mode=` 分别稳定为 `shift` / `scissor`，说明确实跑在预期路径上。
5. **功耗未直接测量**：250ms 粒度的电流差不可分辨；用"整进程 CPU 时间/次"作代理，
   两组 204 vs 210ms（−2.7%，噪声内），可认为功耗等价。

## 5. 结论

* P1 相对 0.86 的 scissor：**帧率 +4.9%（不显著）、p50 持平、CPU −2.7%（不显著）、
  内存 +1.5%（同状态）、启动无差异** → 性能**等价**。
* 因此 P1 的验收线应是"不劣化 + 视觉正确"，而不是"更快"；本次两条都满足（视觉像素级验收
  仍需按 `mobile_vulkan_migration.md` §7.2 在真机抽帧确认）。
* 真正的性能收益要从别处拿：快照 `_RenderPage` 的复用/上限（当前 `_cache` 无 LRU）、
  首页并发封面解码、`AddBooksDeferred` 的批量布局等。
